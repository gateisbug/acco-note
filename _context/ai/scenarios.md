# acco-note 핵심 사용자 시나리오 초안

[사용자 요구사항](../user/prd.md)을 바탕으로 첫 사용부터 거래 관리, 고정지출, 환불, 목표 관리, 데이터 복원까지의 흐름을 정리합니다. 화면 이름과 버튼 배치는 아직 정하지 않았으며, 아래 순서는 사용자의 행동과 시스템의 결과를 나타냅니다.

기본 흐름과 완료 조건은 확정 요구사항을 구체화한 검토 초안입니다. 각 시나리오의 **결정 필요** 항목은 미확정이며, 이 문서 작성만으로 사용자 요구사항에 추가되지 않습니다. 예시 금액과 날짜는 설명용입니다.

모든 시나리오의 날짜·시간 입력·표시·판단과 기간별 집계는 한국 시간(Asia/Seoul)을 기준으로 한다. 기기의 현지 시간대가 달라도 동일한 기준을 적용한다.

## 1. 첫 사용과 첫 거래 등록

**목표:** 로그인 없이 가계부를 시작하고 첫 지출을 저장한다.

**시작 조건:** 현재 브라우저에 가계부 데이터가 없다.

### 기본 흐름

1. 사용자가 가계부를 연다. 회원가입이나 로그인을 요구하지 않는다.
2. 사용자는 제공된 기본 카테고리를 확인한다. 필요하면 수입 또는 지출 카테고리를 직접 추가하거나 이름을 수정한다.
3. 사용자는 결제수단에 ‘생활비 카드’를 등록한다. 실제 카드 연결이나 계좌 인증은 요구하지 않는다.
4. 사용자는 한국 시간 기준 오늘이 기본값인 날짜를 확인하거나 변경하고, 지출 유형, 12,000원, ‘점심’을 입력한다.
5. 선택 항목으로 카테고리와 ‘생활비 카드’를 지정하고 저장한다.
6. 시스템은 거래를 IndexedDB에 저장하고 해당 날짜의 내역에 표시한다.

### 대안 흐름과 예외

- 카테고리와 결제수단을 준비하지 않아도 필수 항목만 입력하여 거래를 등록할 수 있다.
- 필수 항목 누락이나 잘못된 입력이 있으면 해당 항목 바로 아래에 이유를 표시하고, 입력한 내용을 유지한 채 저장을 막는다.
- 사용자가 수입을 등록할 때도 날짜, 유형, 금액, 내역명을 입력하고 카테고리와 메모를 선택적으로 작성한다.
- 저장 공간 부족이나 브라우저 저장 제한으로 저장할 수 없는 경우의 안내와 입력 보존 방식은 결정이 필요하다.

### 완료 조건

- 계정이나 백엔드 서버 없이 첫 거래가 저장된다.
- 내역명이 비어 있거나 금액이 0원·음수·소수이면 해당 항목 아래에 오류 이유가 표시되고 거래가 저장되지 않는다. 다른 입력값은 유지되며 오류를 수정한 뒤 정상적으로 저장할 수 있다.
- 새 거래의 날짜 기본값은 기기의 현지 시간대와 관계없이 한국 시간 기준 오늘이다.
- 오늘·과거 날짜로 신규 거래를 등록할 수 있으며, 저장 즉시 확정하여 입력한 거래일의 통계와 해당 기간의 예산 집계에 반영한다.
- 카테고리·메모·결제수단 미선택이 거래 등록을 막지 않는다.
- 같은 브라우저에서 다시 열었을 때 저장한 내역을 조회할 수 있다.
- 기본 카테고리 제공 과정에서 사용자 카테고리가 덮어써지지 않는다.

**결정 필요:** 기본 진입 화면, 기본 카테고리 목록, 최초 안내 내용, 저장 실패 처리.

## 2. 거래 등록 후 조회와 수정 및 삭제

**목표:** 일상적인 수입과 지출을 기록하고 잘못 입력한 내역을 바로잡는다.

**시작 조건:** 사용자가 거래를 작성할 수 있으며, 예시 거래에는 환불이나 고정지출 연결이 없다.

### 기본 흐름

1. 사용자는 날짜, 지출 유형, 12,000원, ‘점심’을 입력하고 ‘생활비 카드’를 선택해 저장한다.
2. 해당 일의 거래 내역을 열어 등록한 거래를 확인한다.
3. 주별·월별 조회에서도 해당 거래를 확인한다.
4. 실제 결제액이 13,000원임을 확인하고 기존 거래의 금액을 수정한다.
5. 시스템은 같은 거래의 금액을 갱신하며 관련 지출 집계와 예산 사용액에 변경을 반영한다.
6. 사용자가 거래 삭제를 선택하면 삭제 확인창을 표시한다. 사용자가 확인하면 거래를 삭제하고 관련 통계와 예산 집계에서 즉시 제외한다.

### 대안 흐름과 예외

- 사용 중인 카테고리나 결제수단을 보관 처리하면 기존 거래의 연결은 유지하고 새 거래의 선택 목록에서는 제외한다.
- 기존 거래에서 이미 연결된 보관 카테고리·결제수단을 유지한 채 금액·메모 등 다른 필드를 수정할 수 있다. 보관된 항목을 새 거래 또는 기존 거래에 새로 연결할 수는 없다.
- 삭제 확인창에서 취소하면 거래와 관련 집계를 그대로 유지한다.
- 필수 항목 누락이나 잘못된 입력은 해당 항목 바로 아래에 이유를 표시하고, 입력 내용을 유지한 채 저장을 막는다.
- 초기 버전은 거래 삭제 전 확인만 제공한다. 삭제 후 실행 취소·휴지통·개별 거래 복구는 지원하지 않는다.
- 고정지출 생성 거래를 삭제하면 시나리오 3의 회차 처리 규칙을 적용한다. 환불 연결 원거래 삭제는 시나리오 4를 함께 적용한다. 환불이 연결된 원거래는 날짜·금액 수정을 막고 연결 환불을 모두 삭제한 뒤 수정할 수 있다. 고정지출 생성 거래의 날짜를 변경해도 원래 회차 연결을 유지하며, 실제 집계는 변경한 거래일로 옮긴다.
- 미래 날짜로 수입 또는 지출을 등록하면 예정 거래로 저장한다. 예를 들어 다음 달 구매 예정액 30,000원을 입력해도 확정 전에는 실제 지출과 예산 사용액이 증가하지 않는다.
- 예정일이 되면 사용자 확인 없이 자동 확정한다. 앱 미실행 중 예정일이 지난 거래는 다음 실행 시 원래 예정일의 거래로 반영한다.
- 날짜 도래는 한국 시간(Asia/Seoul)을 기준으로 판단하며, 예정일 00:00부터 자동 확정 대상이 된다. 기기의 현지 시간대가 달라도 같은 기준을 적용한다.
- 일반 거래의 날짜를 한국 시간 기준 미래로 변경하면 예정 상태로 전환하고 기존 실제 집계에서 제외한다. 오늘·과거로 변경하면 확정 상태로 전환하여 변경된 날짜의 집계에 반영한다.

### 완료 조건

- 수정 시 새 거래가 중복 생성되지 않는다.
- 거래 수정 중 입력 오류가 있으면 해당 항목 아래에 이유를 표시하고 수정 중인 입력값을 유지한다. 오류가 해결되기 전에는 저장된 기존 거래와 통계·예산 집계를 변경하지 않는다.
- 지난달 날짜로 지출 12,000원을 신규 등록하면 즉시 확정되어 지난달 해당 날짜의 지출과 지난달 예산 사용액에 12,000원이 반영된다. 등록한 시점의 이번 달 집계에는 포함되지 않는다.
- 일반 확정 지출 13,000원의 날짜를 미래로 변경하면 기존 날짜의 실제 지출 및 예산 사용액에서 13,000원이 빠지고, 예정 거래로 유지된다.
- 해당 예정 거래를 오늘·과거 날짜로 변경하면 변경된 날짜의 실제 지출 및 해당 월 예산 사용액에 13,000원이 한 번 반영된다. 확정 거래를 다른 오늘·과거 날짜로 옮겨도 이전 날짜 집계에서 제거하고 새 날짜에만 반영한다.
- 미래 날짜로 새로 등록한 수입·지출은 예정 상태이며, 확정 전에는 실제 수입·지출 통계와 예산 사용액에 포함되지 않는다.
- 거래 금액은 원화로 1원 이상 999,999,999원 이하의 정수만 저장할 수 있다. 0원·음수·소수 및 상한 초과 금액은 등록과 수정 모두에서 허용하지 않는다.
- 다른 입력이 유효할 때 금액 999,999,999원, 내역명 100자, 메모 1,000자는 저장할 수 있다. 금액 1,000,000,000원, 내역명 101자 또는 메모 1,001자는 해당 항목 아래에 오류 이유를 표시하고 입력 내용을 유지한 채 저장을 막는다. 등록과 수정에 같은 제한을 적용한다.
- 수입·지출은 금액의 부호가 아닌 유형으로 구분하며, 환불은 원거래에 연결한 별도 기록으로 처리한다.
- 12,000원을 13,000원으로 수정하면 해당 거래가 속한 지출 집계는 1,000원 증가한다.
- 수정된 거래를 삭제하면 그 거래의 13,000원이 집계에서 빠진다.
- 삭제 확인 전에는 거래를 제거하지 않으며, 취소하면 거래 및 통계·예산 집계가 변하지 않는다.
- 삭제를 확인하면 거래가 제거되며, 실행 취소나 휴지통을 통한 개별 복구 기능은 제공하지 않는다. JSON 백업의 전체 복원은 시나리오 7의 별도 규칙을 따른다.
- 예정 거래를 삭제해도 실제 집계는 변하지 않으며, 해당 거래는 예정일 도래 후에도 자동 확정되지 않는다.
- 사용 중인 분류나 결제수단의 보관이 기존 거래를 삭제하지 않는다.
- ‘생활비 카드’와 ‘식비’가 보관된 뒤에도 해당 항목이 연결된 기존 점심 거래의 금액을 12,000원에서 13,000원으로 수정할 수 있고, 기존 결제수단·카테고리 연결은 유지된다. 두 보관 항목은 새 거래나 다른 기존 거래에 새로 선택할 수 없다.

**결정 필요:** 환불 기록 자체의 수정·삭제 세부 방식. 검색·필터는 아직 제안 단계이므로 이 흐름의 필수 조건에 포함하지 않는다.

## 3. 고정지출 예정 관리와 자동 확정

**목표:** 고정지출 예정 회차를 관리하고 예정일에 자동으로 지출을 반영한다.

**시작 조건:** 시작일과 매월 반복을 설정한 고정지출이 별도로 등록되어 있고, 해당 날짜에 통신비 50,000원 예정 회차가 있다. 고정지출은 매일·매주·매월·매년 중 반복 주기를 선택하며 시작일은 필수, 종료일은 선택이다.

### 기본 흐름

1. 사용자는 예정일 전에 해당 날짜의 가계부에서 통신비 50,000원 예정 항목을 확인한다.
2. 이때 예정액은 실제 지출 합계와 예산 사용액에 포함되지 않고 별도로 표시된다.
3. 청구 예정액이 48,000원임을 확인한 사용자가 해당 회차의 예정 금액을 변경한다.
4. 예정일이 되면 시스템은 사용자 확인 없이 해당 회차와 연결된 실제 지출 48,000원 한 건을 자동 등록한다.
5. 실제 지출 집계와 해당 월 예산 사용액에 48,000원을 반영한다.

### 대안 흐름과 예외

- 예정일 전에 이번 회차를 건너뛰면 자동 확정 대상에서 제외하고 실제 거래를 생성하지 않는다.
- 자동 확정 처리를 반복하거나 앱을 다시 실행해도 같은 회차의 실제 거래는 한 건만 존재해야 한다.
- 앱 미실행 중 예정일이 지난 회차는 다음 실행 시 원래 예정일의 지출로 자동 반영한다.
- 자동 확정 후 금액이 다르면 거래 수정으로 정정한다. 실제로 발생하지 않은 회차는 생성된 거래를 삭제하여 '건너뜀'으로 처리한다.
- 자동 생성된 거래를 삭제하면 해당 금액을 통계·예산에서 제외하고 그 회차를 '건너뜀'으로 처리한다. 해당 회차는 자동 재생성하지 않으며 반복 설정과 이후 회차는 유지한다.
- 반복 설정을 변경하면 아직 확정되지 않은 회차부터 적용한다. 이미 확정된 거래와 개별 수정·건너뜀 처리한 회차는 기존 내용과 상태를 유지한다.
- 고정지출 반복을 중지하거나 반복 설정을 삭제하면 앞으로의 예정 회차를 제거하고 이후 자동 생성·확정을 막는다. 개별 수정한 미래 예정 회차도 제거하며, 이미 확정된 거래와 집계는 유지한다.
- '건너뜀'을 취소하면 한국 시간 기준 오늘·과거 회차는 즉시 확정하고 미래 회차는 예정으로 복원한다. 일반 거래의 삭제 실행 취소와 구분되는 회차 관리 기능이다.
- 개별 회차의 금액 변경이 이후 회차의 기본 금액에 영향을 주는지는 결정이 필요하다.
- 종료일을 지정하지 않은 고정지출은 계속 반복한다.
- 매월·매년 반복의 지정 날짜가 해당 달에 없으면 그달의 마지막 날에 회차를 적용한다. 다음 회차는 보정된 날짜가 아닌 원래 반복 기준일로 계산한다.

### 완료 조건

- 건너뛴 회차는 실제 지출을 만들지 않는다.

- 앱을 며칠 뒤 실행해도 그동안 도래한 회차는 원래 예정일별로 반영되며, 건너뛴 회차는 제외된다.

- 자동 생성된 48,000원 거래를 삭제하면 관련 통계·예산에서 48,000원이 빠지고 회차는 '건너뜀'이 된다. 앱 재실행이나 자동 확정 재처리로 복원되지 않으며 이후 회차는 정상적으로 유지된다.

- 환불이 없는 고정지출 확정 거래 48,000원의 날짜를 지난달에서 이번 달의 오늘·과거 날짜로 변경하면 지난달 집계에서 48,000원이 빠지고 변경한 날짜의 통계·예산에 한 번 반영된다. 원래 회차 연결과 이후 회차는 유지되며, 재실행해도 원래 회차 거래가 중복 생성되지 않는다.
- 날짜를 변경한 거래를 삭제하면 변경 전부터 연결되어 있던 원래 회차를 '건너뜀'으로 처리한다.
- 환불이 없는 고정지출 확정 거래 48,000원을 미래 날짜로 옮기면 예정으로 전환하고 기존 실제 지출·예산 사용액에서 48,000원을 제외한다. 원래 회차 연결은 유지하며, 원래 예정일이 지났더라도 변경한 날짜 전에는 재확정하거나 거래를 중복 생성하지 않는다.
- 변경한 날짜의 한국 시간 00:00부터 해당 거래를 자동 확정하고 변경한 거래일의 통계·예산에 48,000원을 한 번만 반영한다. 앱 미실행 시 다음 실행에서 처리하며, 반복 실행해도 중복 반영되지 않는다.
- 해당 예정 거래를 오늘·과거 날짜로 다시 옮기면 즉시 확정하여 변경한 거래일의 통계·예산에 한 번만 반영한다.

- 월 기본 금액을 50,000원에서 60,000원으로 변경하면 개별 수정하지 않은 미확정 회차는 60,000원으로 변경된다. 이미 확정된 50,000원 거래, 개별적으로 48,000원으로 수정한 예정 회차, 건너뜀 처리한 회차는 그대로 유지된다.
- 반복 설정을 변경해도 개별적으로 변경한 회차의 날짜와 원래 회차 연결을 유지하며, 건너뜀 회차를 다시 생성하지 않는다.
- 통신비 확정 거래 50,000원과 다음 달 예정 회차가 있을 때 반복을 중지하거나 반복 설정을 삭제하면 다음 달 예정 회차는 사라지지만 확정 거래 50,000원과 해당 통계·예산 집계는 유지된다. 앱 재실행이나 날짜 도래로 제거한 예정 회차가 재생성·확정되지 않는다.
- 다음 달 예정 회차의 금액이나 날짜를 개별 수정했더라도 중지·삭제 시 제거한다. 반복 설정의 일반 변경에서 개별 수정 회차를 유지하는 규칙을 중지·삭제에 적용하지 않는다.

- 건너뛴 과거 회차 50,000원을 사용자가 취소하면 해당 회차의 거래일로 즉시 확정되고 통계·예산에 50,000원이 한 번 반영된다. 오늘 회차에도 같은 규칙을 적용하며 반복 처리로 거래나 집계가 중복되지 않는다.
- 미래 회차의 건너뜀을 취소하면 예정으로 복원되고 실제 집계에는 포함되지 않는다. 해당 날짜의 한국 시간 00:00부터 자동 확정 대상이 된다.

**결정 필요:** 개별 회차 금액 변경이 이후 회차의 기본 금액에 미치는 영향.

## 4. 지출의 전액 환불과 부분 환불

**목표:** 기존 구매의 환불을 원거래에 연결하여 지출 집계를 바로잡는다.

**시작 조건:** 환불되지 않은 지출 100,000원이 등록되어 있다.

### 기본 흐름

1. 사용자가 원래 지출 내역을 연다.
2. 부분 환불 30,000원을 기록한다.
3. 시스템은 환불을 해당 원거래에 연결하여 보관한다.
4. 원거래와 환불을 모두 포함하는 조회 범위에서 해당 거래의 순지출은 70,000원으로 반영된다.

### 대안 흐름과 예외

- 별도의 미환불 거래 100,000원에 대해 전액 환불하면 해당 거래의 순지출은 0원이다.
- 환불이 연결된 원거래를 삭제하면 확인창에서 연결 환불도 함께 삭제됨을 안내한다. 확인 시 원거래와 환불을 함께 삭제하고 관련 통계·예산을 갱신하며, 취소 시 모두 유지한다.
- 원거래가 고정지출에서 생성되었다면 해당 회차를 '건너뜀'으로 처리하여 자동 재생성을 막고 이후 회차는 유지한다.
- 지난달 구매를 이번 달에 환불한 경우 어느 달 지출·예산에서 차감할지는 결정이 필요하다.
- 환불이 연결된 원거래의 날짜·금액 수정은 막는다. 수정하려면 연결된 환불 기록을 모두 먼저 삭제해야 한다. 고정지출 생성 거래에도 같은 제한을 적용하며, 수정 가능한 경우 날짜를 변경해도 원래 회차 연결을 유지한다.
- 여러 차례 환불, 원거래 금액보다 큰 환불, 환불 기록 수정·삭제의 세부 방식은 결정이 필요하다.

### 완료 조건

- 환불의 원거래를 식별할 수 있다.
- 원거래 100,000원에 환불 30,000원이 연결되어 있으면 원거래 날짜·금액 변경을 저장할 수 없으며, 원거래·환불·집계를 그대로 유지한다.
- 연결 환불을 모두 삭제하면 일반 원거래의 날짜·금액을 수정할 수 있다. 날짜 변경 시 일반 거래의 예정·확정 전환 규칙을 적용한다.
- 전액 환불과 부분 환불을 모두 기록할 수 있다.
- 원거래와 환불을 모두 포함한 집계에서 환불액이 한 번만 차감된다.
- 원거래 100,000원과 연결된 환불 30,000원을 함께 삭제하면 두 기록이 모두 제거되고, 두 기록을 포함한 조회 범위의 순지출에서 70,000원이 빠진다. 삭제를 취소하면 두 기록과 집계가 유지된다.
- 월별 예산·통계의 완료 조건은 환불 기준일을 결정한 후 보완한다.

**결정 필요:** 집계 기준일, 환불 입력 항목, 복수 환불 및 금액 검증, 환불 기록 자체의 수정·삭제 세부 규칙.

## 5. 월 예산 설정과 사용 현황 확인

**목표:** 월 지출 한도와 실제 사용액을 비교한다.

**시작 조건:** 예시 월에는 환불 없이 실제 지출 600,000원과 미확정 고정지출 예정액 50,000원이 있다.

### 기본 흐름

1. 사용자는 해당 월의 전체 예산을 1,000,000원으로 설정한다.
2. 필요하면 식비 카테고리의 월 한도를 300,000원으로 설정한다.
3. 전체 예산에서 사용액 600,000원, 잔여액 400,000원, 초과액 0원을 확인한다.
4. 고정지출 예정액 50,000원은 사용액에 합산하지 않고 별도로 확인한다.
5. 해당 예정일에 회차가 50,000원 실제 지출로 자동 확정되면 사용액은 650,000원, 잔여액은 350,000원이 된다.
6. 같은 달 실제 지출이 총 1,050,000원에 이르면 초과액 50,000원을 표시한다.

### 대안 흐름과 예외

- 카테고리 한도 없이 전체 예산만 설정할 수 있다.
- 카테고리가 없는 지출도 전체 예산 사용액에는 포함된다.
- 예산을 초과했을 때 잔여액을 음수로 표시할지 0으로 표시할지는 결정이 필요하다.
- 카테고리별 한도 합계가 전체 예산보다 클 때의 허용 여부, 예산 이월 및 환불 반영 시점은 결정이 필요하다.

### 완료 조건

- 미확정 고정지출을 실제 지출과 이중 합산하지 않는다.
- 전체 예산과 설정된 카테고리별 한도에 대해 사용액·잔여액·초과액을 확인할 수 있다.
- 실제 거래 수정·삭제에 따라 해당 예산의 사용액이 갱신된다.

**결정 필요:** 전체 예산과 카테고리 한도의 관계, 초과 시 잔여액 표현, 예산 변경·이월, 환불 반영 시점.

## 6. 저축 목표 생성과 진행률 확인

**목표:** 여러 저축 목적에 대해 사용자가 직접 기록한 저축 실적을 확인한다.

**시작 조건:** 사용자가 저축 목표를 작성할 수 있다.

### 기본 흐름

1. 사용자는 ‘여행 자금’, 목표금액 1,000,000원, 시작일과 목표일을 입력하여 목표를 만든다.
2. 여행 자금 목표에 저축액 200,000원을 기록한다.
3. 시스템은 누적 기록액 200,000원과 진행률 20%를 표시한다.
4. 사용자가 같은 목표에 100,000원을 추가 기록하면 누적액은 300,000원, 진행률은 30%가 된다.
5. 사용자는 별도의 ‘비상금’ 목표를 등록하고 목표별 진행 상황을 확인한다.

### 대안 흐름과 예외

- 목표 날짜와 금액의 유효성 검증 및 동일 저축액의 여러 목표 배분 방식은 결정이 필요하다.

### 완료 조건

- 각 목표는 자신의 저축 기록만으로 진행률을 계산한다.
- 저축액을 기록해도 가계부 수입·지출 통계와 지출 예산 사용액은 변하지 않는다.
- 여러 목표를 서로 구분하여 조회할 수 있다.

**결정 필요:** 저축 기록 필드와 수정·삭제·인출, 목표 간 금액 배분, 초과 달성 표현, 목표 완료·기한 경과 처리.

## 7. JSON 백업과 전체 복원

**목표:** 가계부 데이터를 파일로 보관하고 검증된 파일로 기존 데이터를 전체 대체한다.

**시작 조건:** 브라우저에 기존 데이터가 있고 사용자가 JSON 내보내기와 가져오기를 실행할 수 있다.

### 기본 흐름

1. 사용자는 현재 가계부 데이터를 JSON 파일로 내보낸다.
2. 이후 복원할 JSON 파일을 선택한다.
3. 시스템은 파일을 읽고 구조와 값의 유효성을 검증한다.
4. 검증에 성공하면 대체할 내용을 보여주고 기존 데이터가 전체 대체됨을 알린다.
5. 사용자가 확인하면 파일의 데이터로 기존 데이터를 전체 대체한다. 기존 데이터와 병합하지 않는다.
6. 사용자는 복원한 거래와 관련 데이터를 확인한다.

### 대안 흐름과 예외

- 파일을 읽을 수 없거나 구조·값이 유효하지 않으면 오류를 안내하고 기존 데이터를 유지한다.
- 대체 내용 확인 단계에서 취소하면 기존 데이터를 유지한다.
- 검증 성공 후 적용 중 실패하더라도 기존 데이터를 유지하며, 일부만 대체된 상태를 남기지 않는다.
- 서로 다른 데이터 형식 버전의 호환 범위와 가져오기 전 자동 백업 여부는 결정이 필요하다.

### 완료 조건

- 사용자 확인 전에 기존 데이터를 변경하지 않는다.
- 성공하면 가져온 데이터로 전체 대체되며 이전 데이터가 병합되어 남지 않는다.
- 검증·적용 실패 및 사용자 취소 시 기존 데이터와 연결 관계가 유지된다.
